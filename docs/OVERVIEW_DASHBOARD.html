What we built

Scope

KC's Oracle schema carries no column comments, so the database on its own gives you names and datatypes and very little meaning. We traced meaning back from the Kuali application itself — its ORM mappings, its DataDictionary and its screens — and checked everything against production. What comes out is a source interface organised around business objects rather than tables.

What "technical mapping complete" means, and what it does not

For all four objects the graph, the field mapping and the SQL are built and verified against production. That is not the same as the business decisions being settled. Nothing in this package is marked approved for migration use yet, and the open items are collected further down rather than resolved quietly.

The four business objects

Modules

Each object has its own graph, its own UI-to-database field mapping, its own SQL, and its own rule for picking the record that represents it today. The rules genuinely differ — we worked each one out from production evidence rather than reusing the first one that happened to work.

Versions, and why the row counts look large

Grain

Three of the four objects store every edit as a new sequence, so the physical table is much bigger than the business population. The root datasets are already collapsed to one current record — there is no need to apply a status filter or a MAX(SEQUENCE_NUMBER) on top, and doing so would drop real rows.

Subaward is the sharpest case: 93,061 rows stand behind 3,466 subawards, about 27 versions each. Negotiation is the only object where the physical table and the business population are the same thing.

Three words that are not interchangeable

Selected current record is the row our module rule chose — that is what the root datasets contain. ACTIVE is a KC sequence-status value, and it is only the first test in three of the four rules. Finalized is a KEW workflow state and says where a document reached in routing. The selected current record cannot be defined as "the ACTIVE row", and it cannot be defined as the highest sequence — both have real fallback cases. Every root dataset carries ROOT_SELECTION_RULE saying which branch chose that row.

Award families

Highest risk of being misread

There are three levels in BU's award data, not two, and collapsing any two of them into each other is the biggest risk in the Award module. An Award family — what BU has historically called a grant family — is the root -00001 award together with its child/subaccount awards.

So the 43,202 award records roll up into 15,729 families, about 2.7 awards each. If HRS expects one record per funded project rather than one per account, 15,729 is the number to map against. That choice is open — it is D-17 below.

We checked the structure rather than assuming it. All 15,729 roots end in -00001 and every award ending -00001 is a root. All 43,201 awards share their root's base number. 27,170 non-root awards carry their own ACCOUNT_NUMBER and none shares the root's. Nesting past two levels exists but is rare — 101 awards at level 2 and 3 at level 3, in 21 of 15,729 families. The largest family is 207805-00001 with 216 awards.

BU's 2012 KCRM-SAP functional specification describes the same structure: the parent award became the SAP Grant and each child a Sponsored Program. Production still shows it — no root award carries an ACCOUNT_NUMBER, and BU_GRANT_NUMBER is constant within a family.

A child Award is not a Subaward

A child/subaccount Award is another BU account inside an Award family. A Subaward is a separate business object covering BU's outgoing subaward relationships. They are easy to blur together in conversation, and they map to different places.

How the datasets are shaped

Data contract

Why the queries are separate

We keep people, amounts, terms, special reviews and custom fields in their own queries rather than joining them onto the root. One award with 5 people, 12 terms and 40 custom fields would otherwise come back as 2,400 duplicate award rows. Many-to-one lookups are different — a status or a sponsor cannot multiply anything — so those are folded into the root as code plus description.

Award root → people → amounts → terms → special reviews → custom fields

Every child carries the root keys

So the graph can be reassembled after extraction. Join on the surrogate id (AWARD_ID) when you want exactly the version you are holding; join on the business key (AWARD_NUMBER) across modules, which is what you need when a Subaward's funding link points at an older version than the current one.

AWARD_ID · AWARD_NUMBER · SEQUENCE_NUMBER on every Award child

BU custom fields

KC stores institution-specific fields entity-attribute-value: CUSTOM_ATTRIBUTE holds the definitions, *_CUSTOM_DATA holds the values, linked by CUSTOM_ATTRIBUTE_ID. We resolved BU's 107 configured custom attributes into their labels, groups and datatypes, so the custom datasets present each field by name alongside its value.

AWARD_CUSTOM_DATA 1542 = 'Yes' → CUSTOM_ATTRIBUTE 1542 → "IRB Multi-Site"

Attachments, and one key that looks numeric

Award and Negotiation attachments reach their file through ATTACHMENT_FILE; Institutional Proposal and Subaward attachments reference FILE_DATA directly. The datasets stay metadata only, with identifiers preserved so a file can be located later. FILE_DATA_ID looks like a surrogate key but is a 36-character UUID, so it needs to stay a string through any mapping.

Source keys need to survive the conversion

Every dataset carries its KC business identifier — AWARD_NUMBER, PROPOSAL_NUMBER, SUBAWARD_CODE, NEGOTIATION_ID — plus the internal keys that hold the graph together. Once HRS assigns its own identifiers, the KC key is what ties a converted record back to its source and what re-links objects that were related in KC. Where that key lives on the Huron side, and where the record-level crosswalk lives, is D-20 — we have not built a crosswalk because the Huron half of every row does not exist until load.

A few things we got wrong first, kept because they are the kind of thing that costs someone a day:

The person role lookup doubles the dataset

EPS_PROP_PERSON_ROLE holds two rows per role code, one per sponsor hierarchy. Joined unfiltered it takes Award personnel from 345,600 rows to 691,200. We pin it to the DEFAULT hierarchy, which resolves all 345,600 with nothing unmatched. Institutional Proposal has the same problem — 147,795 rows becoming 295,590.

Do not join PROPOSAL_LOG on INST_PROPOSAL_NUMBER

It looks like the link to the Institutional Proposal and it is not. We tested all 30,646 populated values and none matches a PROPOSAL.PROPOSAL_NUMBER — it is a 7-character legacy identifier where proposal numbers are 8 characters. The real link is the shared PROPOSAL_NUMBER.

FULL_NAME is a copy, not the source

AWARD_PERSONS.FULL_NAME is refreshed from the person record on read. The real person is a KIM identity resolved at runtime and there is no ORM relationship to any person table, so we expose PERSON_SOURCE to make that explicit. SUBAWARD_CONTACT is the same story — no PERSON_ID column at all, and REQUISITIONER_ID populated on all 194,207 rows.

SUBAWARD_TYPE_CODE reuses the Award lookup

There is no SUBAWARD_TYPE table in KCOEUS, which looks like a gap until you read the ORM: subAwardType on SubAward points at AwardType. All 11 codes in production resolve against AWARD_TYPE with nothing unmatched. This is how KC is built, not a workaround on our side.

Delivery

D-18 · not decided

The logical source interface is finished. The physical delivery method is not, and we would rather agree the approach than build something that turns out to be the wrong shape for Huron's tooling. These are options for discussion, not a proposal. One thing worth being explicit about: the SQL in the repository is a definition, not a connection — reading it tells you what you would receive, not how.

Option A

BU runs the queries and delivers files

KCOEUS → curated queries → CSV → secure transfer → Huron staging

For: the simplest security boundary — no Huron access to any BU database, and every extract is a fixed artifact that can be archived, checksummed and reconciled against later.

Cost: extracts are a moment in time. Every mock conversion, rehearsal and cutover needs a fresh run and a fresh transfer.

Option B

Read-only database access to curated views

KCOEUS → migration views → read-only account → approved network path

For: Huron queries directly, so there is no extract-and-ship cycle and the data is always current.

Cost: the heaviest to set up — dedicated least-privilege credentials scoped to the migration views, an approved BU network path, BU security approval, agreed audit and logging. This would never mean sharing the KCOEUS application account.

Option C

A BU-controlled staging schema

KCOEUS → BU extraction → staging schema → Huron read-only access

For: a middle path. Huron gets table-and-SQL access, which suits tooling that wants to query rather than parse files, but never touches the live KC application schema.

Cost: a database or schema to own and a refresh process to run.

Option D

API or managed transfer

KCOEUS → BU extraction → API / object storage / MFT

For: it may be what Huron's tooling already expects, and that would be worth knowing early.

Cost: we have not built any of this and are not assuming it exists.

What would help us most from Huron

1
What does the mapping tooling prefer as a source?
Files, database tables or views, API payloads, or something else it already supports well.
2
If database connectivity is preferred, what does it need?
Supported drivers, which side initiates the connection, source IP ranges BU would need to allow, authentication methods, and whether access is persistent or only during migration windows.
3
If files are preferred, what conventions apply?
Format, delimiter and encoding, encryption at rest and in transit, transfer method, file-size limits, and any naming or layout the tooling expects.
4
What does Huron need over the life of the project?
Current datasets only, repeated mock-conversion extracts, the production cutover extract, or all three. The answer changes how much of this needs to be repeatable rather than one-time.
5
Does Huron need production directly, or would a BU-owned copy meet the requirement?
This one has the largest effect on how long provisioning takes on the BU side, so an early answer helps.
