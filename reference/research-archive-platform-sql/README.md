# Research Archive Platform SQL reference

We copied these SQL files from the Research Archive Platform because they contain useful Kuali/Oracle discovery, extraction, attachment, validation, and reconciliation work that may save time during the BU-to-Huron data exchange. We kept the Oracle SQL separate from PostgreSQL archive queries so nobody mistakes a Research Archive migration for a Kuali extraction script.

These are reference copies. The original repository at `/Users/mukadder/projects/research-archive-platform` remains the source of truth. Changes made here do not flow back to that project, and a query that worked for the archive may still need changes for the Huron migration scope, current Oracle grants, schema synonyms, or target mapping.

## What was copied

- `oracle/` contains 95 reusable Oracle/Kuali discovery and extraction files. Each file keeps its full original relative path beneath this directory.
- `postgres-reference/` contains 6 read-only PostgreSQL queries whose counting, grain, relationship, or reconciliation logic may be useful after adaptation.
- `platform-reference/` was not created. We reviewed the application migrations and schema SQL, but none needed to be copied: they build the Research Archive application rather than extract Kuali data, and the reusable source rules are already represented in the Oracle SQL and read-only reconciliation queries.
- [`SQL_INVENTORY.csv`](SQL_INVENTORY.csv) records all 331 SQL files returned by the requested recursive inventory, including excluded files and generated worktree duplicates.

## Safety review

We scanned the copy candidates for credentials, passwords, tokens, private keys, hostnames, usernames, connection strings, hard-coded BU email addresses, write statements, and apparent extracted output. We found no secrets, connection endpoints, or extracted result sets in the copied files. The copied SQL is SELECT-only. Comments contain Kuali table names, verified BU business rules, and expected reference codes; those are intentional source documentation.

No SQL was executed and no database connection was opened during this copy.

## How to use these files

Oracle files fall into two styles:

- Files under `oracle/oracle/` generally use `KCOEUS.`-qualified objects. They are read-only and can normally run directly when the account has access to those objects and Oracle metadata views.
- Files under `oracle/sql/extract/` generally rely on the connected Oracle schema or synonyms and often begin with SQL*Plus `SET` commands. The SELECT is reusable, but a non-SQL*Plus client may need those commands removed.

No copied Oracle file currently contains a bind variable. Some loader code in the source project adds bind-variable filters around these queries at runtime; that filtering behavior is not part of these standalone SQL files. Placeholder object names in discovery comments must be replaced only after metadata confirms the real owner and object.

PostgreSQL files assume the Research Archive `archive` schema. They are reference-only for this project until table names and grain are mapped to the Huron exchange model.

## Important discoveries by module

### Award

The Award collection preserves version grain instead of flattening one row per award number. Separate queries cover amounts, people, unit relationships, credit splits, terms, contacts, hierarchy, Time and Money, budgets, SAP transmission history, and attachments. Keeping these queries separate avoids multiplying rows when several one-to-many child collections exist for the same Award.

The attachment discovery distinguishes metadata from physical content and documents the `ATTACHMENT_FILE.FILE_DATA` versus external `FILE_DATA.DATA` fallback. It also deduplicates physical files by `FILE_ID`.

### Proposal

Proposal files cover version records, attachments, people and roles, person units, unit contacts, comments, and custom data. The discovery SQL preserves proposal identifiers and the version/sequence fields needed to trace a Huron record back to Kuali.

### Negotiation

Negotiation extraction uses `NEGOTIATION` as the parent and keeps activities, custom data, notifications, and unassociated details as separate child datasets. Lookup joins add status, agreement type, association type, activity type, and location descriptions without dropping the parent when a lookup is missing. Attachment ownership is resolved through `NEGOTIATION_ACTIVITY` because `NEGOTIATION_ATTACHMENT` does not carry the Negotiation ID directly.

### Subaward

Subaward extraction keeps versions, funding, amount history, contacts, custom data, reports, closeout, notepad, notification, template, and attachment datasets separate. The validation package includes source counts, primary-key checks, relationship checks, and lookup coverage useful for migration reconciliation.

### Reference data

The reference queries preserve Unit, Unit Administrator, Person, Rolodex, Comment Type, and Custom Attribute structures. Comments record verified Kuali filtering rules where known. These files are especially useful for resolving codes to descriptions without guessing.

### Protocol

Three Oracle queries preserve Protocol versions, people, and units. They were included because they are reusable Kuali discoveries even though Protocol was not one of the explicitly named modules in the request.

## Duplicate and superseded material

The recursive inventory found 145 SQL files beneath `.claude/worktrees/`. Those are generated checkout copies, not another source of truth, and were excluded. The authoritative source paths are listed separately in the inventory.

Some Oracle files overlap in subject without being byte-for-byte duplicates—for example older module-specific `oracle/<module>/export_*.sql` files and the broader `sql/extract/<module>/` catalog. We retained both when each carries distinct joins, validation, attachment, or discovery knowledge. The inventory does not label either generation as superseded unless the source itself says so.
